## Что сделано

### F1. Текущие дайджесты для неподтверждённого узла

- `get_concept` (`src/tools.ts:636`, `currentDigestsOf`) добавляет блок `current_digests: {claim, status, format_version, source}`:
  - без снимка — `source: "computed"`, `claim = claimDigestOf(summary)`, `status = statusDigestOf(status, epistemic_status)` — существующие экспорты, алгоритм не переписывался;
  - со снимком — `source: "snapshot"`, `claim` из `nodes.claim_digest`; `status` всегда текущий (узлового снимка статуса не существует — задокументировано в типе и описании инструмента).
- `provenance_trace` (`src/provenance.ts`, `provenanceTrace`):
  - тот же `current_digests` у корня; для удалённого корня — `null` (надгробие дайджестов не отдаёт);
  - новый блок `supports[]` — по каждой живой опоре корня `claim_digest`/`status_digest`/`edge_digest` целиком (sha256-hex, 64 символа), ровно то, что ждёт `confirm_supports.items[]`. Отсортировано по `support_id`, кап 50 записей + честный `supports_count`. Для опоры с отсутствующим узлом дайджесты `null` (пара уже репортится как `removed` в `support_check`).
- Превью из 12 символов остались только в `provenance_history`.
- Компактный `understand` дайджестов не содержит (тест 6 защищает).
- Описания `get_concept`/`confirm_supports`/`provenance_trace` в `src/index.ts` называют точные места дайджестов: «в `get_concept.current_digests` и `provenance_trace` (`supports[]`); в компактном `understand` их нет».

**Отклонение от буквы плана:** «блок каждой опоры (`supports[]`)» в `provenance_trace` не существовал — блок добавлен (top-level в ответе, обе стороны direction), а не «расширен превью до полных значений». В `supports[]` отдан и `status_digest` (в плане названы только `edge_digest`/`claim_digest`): `confirm_supports` отказывает без `expected_status_digest` — без него контракт «первое подтверждение из ответов сервера» был бы неисполним.

### F2. Опоры внутри решения в выдаче

- В компактном `understand` (`src/tools.ts`) опора, чьё решение тоже в выдаче, вкладывается в решение: `supports: [{id, name, summary}]` у узла-решения.
- Алгоритм — идемпотентный пересчёт на каждом проходе: (1) fold-set = все выставленные узлы, которых информирует другой выставленный узел; (2) каждый вкладывается под своего первого (по рангу) хоста, который сам не вкладывается. Цепочка `D ← S1 ← S2`: S1 вкладывается в D, S2 остаётся наверху — ничего не теряется, глубина ровно 1.
- Вложенная опора не занимает слот `top_k`: после вкладывания слот дозаполняется хвостом кандидатов (Phase A/B/C: базовое заполнение → вкладывание → дозаполнение с повторным вкладыванием после каждого нового узла).
- `meta.supports_inlined: N`, `returned` считает верхний уровень; токены вложенных опор входят в `tokens_estimated` (проекция считается по финальной форме выдачи).
- Порядок верхнего уровня не меняется; если решение не попало в выдачу, опора остаётся самостоятельным фактом.
- Full-режим `understand` не тронут (вложение — свойство компактной выдачи).

### F3. Bench считает вложенные опоры найденными

- `src/bench.ts`: ранг по объединению — верхний уровень в порядке выдачи, вложенная опора на ранге своего решения; `hit` по наличию в объединении.
- `top_ids` = верхний уровень, затем вложенные id; пометка — новое поле `nested_ids: string[]` (top_ids остался `string[]`, существующие ассерты не тронуты).
- unknown/stale-проверка идёт по всему объединению — вложенная опора не выпадает из учёта (`unknown_supports`/`stale_hits` семантика прежняя).

**Отклонения в фиксстурах (по праву «правится фикстура, а не контракт»):**

1. Тест 7 («удалённый узел — `current_digests: null`»): `get_concept` на удалённом узле падает с `not found` (существующий контракт, тест `get-concept.test.ts` его бдит) — случай покрыт через `provenance_trace` с удалённым корнем.
2. Тест 12 («при top_k: 3 … 3 верхних узла»): при `top_k: 3` поиск возвращает максимум 3 кандидата — после вкладывания одного из трёх дозаполнять нечем, «3 верхних» недостижимы ни при какой реализации. Фикстура переписана в сценарий с тем же смыслом «top_k заполняется верхним уровнем»: 4 кандидата, бюджет на 3 узла, одно вкладывание → 3 верхних узла, не 2.
3. Все новые фикстуры с поиском вызывают `ensureSchema(db)`: без таблицы FTS поиск уходит в LIKE-fallback по всей фразе (как в bench.test.ts), и запросы из нескольких слов не находят ничего.
