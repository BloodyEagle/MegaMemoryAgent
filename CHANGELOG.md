# Changelog

## 2.1.9

Два дефекта, найденные на живом проекте 2026-11-04 (TwonkyGrabber3). Схема БД
не менялась.

### Пустой веб-интерфейс (F1, регрессия с момента появления `{{D3_SRC}}`)

`serve` подставлял в страницу `/vendor/d3.min.js`, но каталога `web/vendor/`
в пакете не было — в tarball'ах 2.1.4–2.1.7 лежит только `index.html`. Итог:
404, `d3 is not defined`, пустой экран при живых данных.

- `web/vendor/d3.min.js` (d3 v7.9.0, ~280 КБ) теперь в пакете и в tarball'е —
  обозреватель работает офлайн.
- Если вендорного файла на диске нет и `MEGAMEMORY_D3_URL` не задан —
  фолбэк на CDN (`https://cdn.jsdelivr.net/npm/d3@7/dist/d3.min.js`) с
  напечатанной строкой `d3: локальный файл не найден, используется CDN`.
  Молчивого 404 больше не бывает.
- `MEGAMEMORY_D3_URL` остаётся приоритетнее всего (офлайн-установки с
  самодельным зеркалом).
- `/api/health` и `doctor` несут `d3_source`: `local` / `cdn` / `env`.

### Опоры-заглушки не принимаются (F2)

`create_concept` принимал любой текст, поэтому агент закрывал требование опоры
узлами вида «File-fact node for … — created as a provenance support». У
заглушки нет утверждения: она не может ни подтвердиться, ни устареть, но в
`stats` и `weak_links` выглядит как подтверждение. На TwonkyGrabber3 так
появились 8 из 11 опор.

- `create_concept` отклоняет `summary`-заглушку: шаблон (`file-fact node`,
  `provenance support`, `file: …`) либо короткий текст без глагола-утверждения.
  Проверка не применяется к `kind=module` и диджестам. Отказ объясняет: файл
  передавай как `evidence: [{ref, why}]`, узел — только для мысли, которую
  нельзя выразить ссылкой.
- Обход для осознанных случаев — `allow_stub: true`: узел запишется с
  `epistemic_status = "stub"` и останется видимым как слабое звено.
- Уже записанные заглушки не удаляются, а помечаются: новый тип
  `stub_support` в `weak_links` (решение опирается на узлы без утверждения),
  поле `quality: "stub" | "claim"` у каждой опоры в `provenance_trace.supports[]`,
  строка `Stub supports: N` в `stats` и `doctor`.

### Сниппет: файл — это ref, а не узел (F3)

В блок опор онбординг-сниппета добавлено правило: опора на файл — это
`evidence: [{ref: "path:строки", why}]`, а не новый узел; узел-опору создавай
только для мысли, которую нельзя выразить ссылкой. Лимит 60 строк сохранён.

## 2.1.7

Два дефекта первого реального прогона провенанса (аудит живой базы 2026-11-04,
`audit-before-confirm-report.md`). Схема БД не менялась — всё считается на
чтении (`user_version` остаётся 11).

### Дайджесты до первого подтверждения (F1)

`get_concept` и `provenance_trace` не отдавали `claim_digest` узла без
снимка, а `confirm_supports` требует `expected_claim_digest` — первое
подтверждение было невозможно без воспроизведения алгоритма хеширования вне
сервера (в аудите так и вышло). Теперь:

- `get_concept` несёт `current_digests` — `{claim, status, format_version,
  source}`. Для неподтверждённого узла `source: "computed"` (дайджест текущей
  формулировки — то, что нужно первому подтверждению); для подтверждённого
  `source: "snapshot"` (дайджест подтверждённой формулировки из снимка —
  устаревшее значение честно отклонится `version_conflict`). `status` всегда
  текущий: узлового снимка статуса не существует.
- `provenance_trace` несёт тот же `current_digests` у корня (null для
  удалённого корня — надгробие дайджестов не отдаёт) и `supports[]` — полные
  `claim/status/edge` дайджесты каждой живой опоры, ровно то, что ждёт
  `items[]` подтверждения. Не превью из 12 символов — они остались в
  `provenance_history`. Список ограничен 50 записями с честным
  `supports_count`.
- Компактный `understand` дайджестов не содержит — это плата токенами на
  каждом чтении.

Контракт: значение `current_digests.claim`, переданное в `confirm_supports`,
принимается без `version_conflict`, если узел не менялся между чтением и
подтверждением.

### Опоры внутри решения в выдаче (F2)

После появления 11 узлов-опор `hit_rate@1` на живой базе упал с 0.93 до
0.71: опора содержит термины запроса дословно и вытесняет своё решение с
первого места. Теперь в `understand` (компактный режим) опора, чьё решение
тоже в выдаче, убирается с верхнего уровня и вкладывается в решение
(`supports: [{id, name, summary}]` у узла). Глубина — один уровень (опора
опоры остаётся наверху); если решение не попало в выдачу, опора остаётся
самостоятельным фактом; порядок верхнего уровня не меняется; освободившийся
слот дозаполняется (top_k не проседает); токены вложенных опор входят в
`tokens_estimated`; `meta.supports_inlined` — сколько вложено, `returned`
считает верхний уровень. Множество доступных id не уменьшается.

### Bench: вложенные опоры считаются найденными (F3)

Ранг и `hit` считаются по объединению: верхний уровень в порядке выдачи,
вложенная опора — на позиции своего решения. `top_ids` включает вложенные id
(отдельно помечены в `nested_ids`); проверка unknown/stale идёт по всему
объединению — вложенная опора не выпадает из учёта.

### Документация (F4)

README (RU/EN) и `docs/bench-protocol.md` — раздел «почему `hit_rate@1`
может упасть после пополнения базы» (`supports_inlined`); `guide` —
дайджест решения берётся из `get_concept.current_digests`, руками считать не
нужно; описания `get_concept`/`confirm_supports`/`provenance_trace` называют
точные места, где живут дайджесты (в компактном `understand` их нет).

Живой прогон (копия базы 2026-11-04, тот же вопросник, `--baseline files
--files-top 3 --ref-root project`): `hit_rate@1` 0.71 → **0.93**, медиана
r(files) 82.33 → 84.91, graph-токены 19 059 → 18 892 (−0.9%),
`unknown_supports` 19 → 20 вхождений при том же объединении из 4 решений
(+1 — дозаполнивший слот узел q2 вытащил в выдачу ещё одно найденное
неподтверждённое решение; очередь подтверждений не выросла).

19 новых тестов; ассерты прежних не тронуты. Полный прогон зелёный
(`db.test.ts` исключён на Windows, 4 флака 5s-таймаутов перепроверены в
изоляции).

## 2.1.6

Честные цифры `bench`: пять дефектов замера, из-за которых цифра была либо
завышена, либо не поддавалась проверке (по итогам живого прогона 2.1.5:
`hit_rate 1.00` при ранге 6, медиана ×50.93). Схема БД, провенанс и
MCP-инструменты не тронуты.

### Ранг и hit_rate@1 (F1)

`hit: yes` значил «ожидаемый узел где-то в топ-10» — цифра читалась сильнее,
чем есть. `QuestionResult` получил `expected_rank` (1-based позиция лучшего
совпавшего `expect_nodes` в выдаче; при двух ожидаемых считается по лучшему)
и `top_ids` (id в порядке выдачи). В таблице — колонка `rank`, в итоге —
`hit_rate@1` рядом с прежним `hit_rate` (топ-10, обратная совместимость).
Всегда `hit_rate@1 ≤ hit_rate`.

### Рефы с суффиксом строки (F2)

`src/db.ts:9` и `src/db.ts:605-643` раньше не статились — `statSync` получал
строку с `:N`, и реф всегда падал в `missing`. `splitRefSuffix` отрезает
` :N` и `:N-M` только когда хвост после последнего `:` — цифры или
цифры-цифры; двоеточие диска (`C:\...`, позиция 1) и двоеточие внутри имени
(`a:b.ts`) не режутся. Все варианты суффикса считаются тем же файлом, что и
голый путь — токены не удваиваются; пустой суффикс (`src/db.ts:`) — честный
`missing`, не падение.

### Несколько корней рефов (F3)

Одна база держит три конвенции путей (`src/...` от корня репозитория,
`project/src/...` и `plans/...` от рабочего каталога) — ни один cwd не
покрывал все: от cwd разворачивалось 27/45 рефов, от корня репо 18/26.
Новый флаг `--ref-root PATH` (повторяемый) и поле `ref_roots` в вопроснике
(на вопрос, перебивает флаг). Порядок резолва: корни вопроса → `--ref-root`
→ git-корень (`git rev-parse --show-toplevel`, если это репозиторий) → cwd;
побеждает первое попадание, детерминированно. Кэш «реф → путь» на весь
прогон — тот же реф не статится по 14 раз. В итоге — строка
`refs: resolved N/M (roots: ...)`; в строке вопроса `missing:N` остаётся.

### Честный baseline: --files-top (F4)

`--baseline files` складывал **все** `file_refs` найденных узлов — десятки
тысяч токенов и ×50, которых в жизни не бывает: живой агент читает два-три
файла. `--files-top N` (по умолчанию 0 = все, прежнее поведение) считает
baseline по первым N уникальным файлам в порядке выдачи узлов (внутри узла —
порядок `file_refs`). В отчёте второе отношение `r(files-top)` и медиана по
нему, в таблице — колонка `files(top)`. Всегда `r(files-top) ≤ r(files)`;
если N больше числа уникальных файлов — равенство.

### unknown_supports и stale по вопросам (F5)

Прежний агрегат по всему топ-10 (54 при восьми решениях в базе) не отвечал
на вопрос «к какому вопросу и какие именно решения». `QuestionResult` несёт
`unknown_support_ids` и `stale_ids`; в строке вопроса — заметки `unk:N` и
`st:N`, в итоге — сумма и объединение id (до 10, дальше `+N`).

### Холодный старт (F6)

Первый вопрос живого прогона — 17.7 с против 14–24 мс остальных: грузится
модель эмбеддингов. Если время первого вопроса больше чем в 5 раз превышает
медиану остальных — в notes первой строки `cold-start`, в итоге строка
`warmup: ...s (model load, excluded from median time)` рядом с медианой без
него. Время не выбрасывается молча — печатаются обе цифры.

### Документация (F7)

`--help`: `--ref-root`, `--files-top`, `hit_rate@1` в строке bench. README
(оба языка) и `docs/bench-protocol.md` — раздел «Как читать цифры»:
`hit_rate@1` против `@10`, `r(files)` против `r(files-top)`, почему ×50 из
«всех рефов» не бывает в жизни, что значит `unknown_supports`. В `guide` —
одна строка: для честной цифры — `--files-top 3`, и смотри `hit_rate@1`.

### Тесты

20 новых: ранг и hit_rate@1 (узел первым/третьим/без expect_nodes), рефаксы
с суффиксом (тот же файл, Windows-путь, двоеточие в имени, пустой суффикс),
корни (git-корень при cwd в подкаталоге, приоритет `--ref-root` над cwd и
`ref_roots` вопроса над флагом, один реф в двух корнях — один файл), files-top
(меньше токенов и r, N больше числа файлов, порядок узлов а не алфавит),
unknown/stale по вопросам (unk:1 с id, подтверждённое решение unk:0, сумма
равна итогу), холодный старт (обе цифры, cold-start только в первой строке),
`--help` и README ×2. Снапшот хелпа обновлён. Ассерты прежних тестов не
менялись; полный прогон зелёный (`db.test.ts` на Windows исключён —
зависание libsql, известное с 2.1.3).

Онбординг агента с первого запуска и измеритель экономии. Схема не меняется.

### Проблема

Сниппет в `AGENTS.md` описывал базовый цикл understand → work → update, но
про провенанс (2.x) не говорил ничего: агент создавал решения без опор, не

### Онбординг: провенанс в сниппете (F1)

В `AGENTS_MD_SNIPPET` добавлены четыре темы — весь блок остался в пределах
60 строк (тест следит за объёмом: блок живёт в контексте каждой сессии,
распухший начнут игнорировать):

- **опоры при записи** — `evidence: [{node | ref, why}]` в том же вызове,
  что и создание; `why` — что именно в опоре поддерживает вывод;
  `file_refs` без опор не считаются (auto_ground выключен по умолчанию),
  автовыведенные опоры — черновик, не проверка;
- **подтверждение версий** — `confirm_supports` с digest'ами из ответов
  `provenance_trace`/`get_concept`; чтение состояний `support_check.state`
  (`unknown` и `incomplete` — не «всё хорошо»), реакция на `changed`,
  честная неполнота `truncated_by`;
- **устаревшие инструкции** — `instructions_stale: true` → `megamemory install`;
- **что записывать** — одна мысль — один узел, конкретика в саммари,
  примеры хорошего и плохого узла.

### `megamemory guide` (F2)

Команда печатает тот же текст, что уходит в `AGENTS.md`, плюс пример сессии
(старт → вопрос к графу → запись с `evidence` → подтверждение) и раздел
«Измерение пользы». Сниппет переехал в `src/guide.ts` — одна константа, два
потребителя: install пишет её в AGENTS.md, guide печатает; разойтись они не
могут (тест сверяет).

### `megamemory bench` (F3)

Числа вместо ощущений: сколько токенов стоит сориентироваться и ответить по
графу против альтернативы.

```
megamemory bench --db <база> --questions q.jsonl --baseline files|te|both
```

- `files` (по умолчанию) — токены файлов из `file_refs` найденных узлов;
  файлы больше лимита (200 КБ, `--file-limit`) считаются по размеру с
  пометкой `estimated`;
- `te` — вывод внешнего структурного инструмента (`--te-cmd` с `{query}`;
  `te_cmd` и `lang` можно задать на вопрос), `baseline_te_tokens` из файла
  вопросов используется без запуска команды;
- `both` — оба отношения рядом: где память выигрывает, а где структурный
  инструмент — верный вызов; разбивка медиан по `lang`.

В таблице по вопросам и в итоге: `ratio = baseline_tokens / graph_tokens`,
время до графа и до baseline, `hit_rate` (ожидаемые узлы в топ-10),
`stale_hits` (найденные узлы с `support_check.state = changed`),
`unknown_supports` (найденные решения без подтверждения). Вопросы, где граф
проиграл (`ratio < 1`), печатаются, а не прячутся. Честная оговорка печатается
каждым прогоном: измеряется стоимость ориентации, а не качество ответа —
дешёвый неверный ответ не экономия.

### Протокол A/B и документация (F4, F5)

`docs/bench-protocol.md` — ручной протокол живого сравнения двух сессий
(10 вопросов, медианы, положительный результат только при выигрыше и по
токенам, и по правильности) и раздел о том, что `bench` меряет по данным
графа, а протокол — поведение живого агента; одно другое не заменяет.
README (оба языка) — раздел «Измерение пользы» с тремя режимами; в сниппет
и `guide` добавлен абзац про `bench`; `--help` перечисляет `bench`,
`--baseline files|te|both`, `--questions`, `--te-cmd`, `--file-limit`.

### Тесты

19 новых: 11 на `bench` (ratio, промахи, лимит файлов, суммы, пустой
вопросник, te-заглушка, шаблон без `{query}`, both, preset без запуска
команды, приоритет `te_cmd` вопроса и разбивка по языкам, stale/unknown

## 2.1.4

Единый `--db` во всех командах CLI и запрет тихого создания базы
диагностическими командами. Схема не меняется.

### Проблема

`--db` был заявлен в хелпе только для `stats`/`conflicts`/`resolve` (и
разобран ещё в `merge` со своими позиционными аргументами). Остальные
команды, открывающие базу — `doctor`, `migrate`, `repair-ids`, `reembed`,
`digest`, `export`, `eval`, `consolidate` — флаг молча игнорировали и брали
путь из `MEGAMEMORY_DB_PATH` или из `./.megamemory/knowledge.db` в текущем
каталоге. Опечатка в пути создавала пустую базу: `doctor` рапортовал «0
проблем», отчёты строились не по той базе, копию нельзя было проверить, не
входя в её каталог.

### Единый резолвер пути

Новый модуль `src/db-path.ts` (`resolveDbPath`). Порядок источников:
`--db PATH` / `--db=PATH` → `MEGAMEMORY_DB_PATH` (пустая строка считается
незаданной) → `<cwd>/.megamemory/knowledge.db`.

- `--db` дважды — ошибка о неоднозначности, а не «последний выиграл».
- `--db` без значения, `--db=` без значения, каталог вместо файла —
  отдельные внятные ошибки с путём в тексте.
- Несуществующий файл → «База не найдена: <путь>. Укажи --db,
  MEGAMEMORY_DB_PATH или запусти из каталога проекта» — и **файл не
  создаётся**.
- `allowCreate` остался только у `serve` и MCP-режима: первая установка
  законно создаёт базу.

Все команды, открывающие базу, переведены на резолвер; `merge` не тронут —
у него позиционные аргументы для нескольких баз. В хелпе `--db` описан один
раз как глобальная опция, пометка «для stats/conflicts/resolve» убрана; у
каждой подкоманды, работающей с базой, в строке указан `--db PATH`.

### Тесты

16 новых: приоритет источников (`--db` > env > cwd), `--db=`, ошибка без
создания файла (включая сквозной `doctor` на пути с опечаткой — exit 1 и
файл не появился, а не «0 проблем» на пустой базе), двойной `--db`,
каталог вместо файла, регресс `allowCreate` у `serve`, снапшот хелпа.

## 2.1.3

Два отложенных пункта из §10 дизайна снимка обоснования (plan-4-fingerprint-design-v2):
журнал ревизий опор и digest внешних артефактов. Схема поднимается до **v11**
(миграция на открытии, идемпотентная, старые базы получают новые таблицы и
колонку; путь 10 → 11 проверен на копии живой базы — она прошла весь путь
7 → 11 одним открытием, данные целы, doctor зелёный). Третий пункт §10 —
bootstrap старых решений — сознательно не сделан: массовое подтверждение
непроверенных решений стёрло бы сигнал `unknown` вместе с настоящими
расхождениями.

### Журнал ревизий опор (F1)

Снимок отвечает на вопрос «изменилось ли с момента подтверждения», но не на
«что было раньше и когда». Теперь у каждой пары «решение—опора» есть цепочка
версий — таблица `support_revisions`.

- **Журнал пишется там же, где пишется снимок** — правило, а не перечень мест:
  `confirm_supports`, carve-out `create_concept` с `evidence` и перенос при
  merge. Мутации и чтения в журнал не пишут — инвариант «мутация не
  подтверждает» не тронут.
- Первое подтверждение пары открывает цепочку записью `agent/confirmed`;
  повторное подтверждение с другим digest'ом уносит старую версию в журнал как
  `superseded/reconfirmed` (с её собственным временем подтверждения); пустое
  подтверждение пишет `removed`; перенос при merge — `import`, а при
  пере-якорении ребра на новый rowid — `import/edge_relinked`.
- **Ретеншн: 50 ревизий на пару и 365 дней.** Лимит пары подрезается при
  записи (один индексированный DELETE), дневная чистка едет на записях пачками.
- Новый инструмент `provenance_history(decision_id, support_id?, limit=20)`:
  по каждой паре цепочка newest-first — `confirmed_at`, `source`, `reason`,
  превью digest'ов (12 символов) и признак «это текущая версия». Никаких тел
  узлов — только версии.
- Старые базы начинают с **пустым журналом**: история не выдумывается, цепочка
  открывается первым подтверждением после обновления.

### Digest внешнего артефакта (F2)

Опора может ссылаться на файл или коммит; если файл переписали, саммари могло
остаться прежним — и снимок молчал. Новый инструмент `check_artifacts` и
таблица `node_artifacts`.

- **Только явный вызов**: ни чтение узла, ни трассировка файлы не читают и не
  хешируют — фоновое хеширование на каждом чтении это и приватность, и
  стоимость. `file` — sha256 содержимого потоком; `git_blob` (`<rev>:<path>`) —
  `git rev-parse` + `git cat-file`, только если каталог под git. Отсутствующий
  файл — запись `missing` (в таблице `digest: null`, прежнее значение остаётся
  в `prev_digest`), не падение. `max_files` ограничивает работу, лишнее —
  `truncated: true`.
- **Вердикт по содержимому, не по часам**: `confirm_supports` сохраняет digest
  наблюдённых артефактов опоры в сам снимок (`support_baselines.artifacts_digest`,
  NULL = ничего не наблюдалось — честно нет сигнала). `support_check` сравнивает
  текущее наблюдение с сохранённым: первая проверка после подтверждения не
  даёт ложного «изменилось», двойное изменение не теряет сигнал (сравнение с
  подтверждённым, а не с предыдущим наблюдением), повторное подтверждение
  снимает сигнал.
- `support_check` различает `support_changed` и `artifact_changed` — это не
  замена саммари, а изменившийся источник. В `weak_links` отдельный тип
  `artifact_changed` с путём и превью обоих digest'ов; `prev_digest`/`changed_at`
  в таблице — только для текста предупреждения, на вердикт не влияют.

### Ограничения

- **`kind = 'url'` не поддерживается** сознательно: сетевые запросы из
  MCP-сервера — отдельное решение с таймаутами, прокси и приватностью.
- Bootstrap старых решений не сделан: старые решения остаются `unknown`, пока
  агент их явно не подтвердит. Массовое подтверждение — отдельная команда с
  `confirmed_by: 'bootstrap'` и отдельной метрикой, не смешанной с проверенными.

### Doctor и миграция

- Doctor проверяет наличие `support_revisions` и `node_artifacts` и печатает
  число ревизий и наблюдений артефактов (отсутствующая таблица — проблема, а
  не заметка).
- Миграция идемпотентна; открытие базы v10 (и старше) создаёт обе таблицы и
  колонку `artifacts_digest`, данные и снимки целы, журнал стартует пустым.

## 2.1.2

Четырнадцать правок по двум ревью (Astra целиком, Sol по `support-baselines.ts`).
Новых возможностей нет; схема не меняется. Одно изменение поведения: слияние
баз теперь фиксирует расхождение живого ребра и надгробия как конфликт
`needs_merge`, а не решает его порядком входов (см. «Слияние»).

### Падения и тихая потеря (F1, F3, F6, F14)

- **Два `evidence` с одним `ref`** больше не роняют `create_concept`: повтор
  переиспользует уже запланированный узел-источник (одна опора, один снимок),
  первая формулировка `why` побеждает.
- **Удалённый корень терминален** и в обходе провенанса: `provenance_trace`
  показывает заглушку и не раскрывает исторические рёбра (раньше
  `D → F → G` по удалённому `D` выдавал `F` и `G`, в том числе в режиме
  `retrospective`).
- **Нестроковые ожидания в `confirm_supports`** (`expected_claim_digest`,
  `expected_edge_digest`) дают штатный `version_conflict` с внятным текстом,
  а не `TypeError` на `.slice()`; все три ожидания проверяются по типу до
  сравнения.
- **`provenance_metrics` читает один снимок**: весь вызов идёт в одной
  читающей транзакции, конкурентное удаление между выборкой и проверкой
  больше не роняет вызов на `null.state` — исчезнувший вход учитывается как
  непроверенный.

### Честность метрик и ответа (F4, F5, F13)

- **`unknown` внутреннего узла-факта виден**: у любого показанного узла с
  `informed_by`, чьи опоры не подтверждены снимком, появляется запись
  `support_unreviewed` (раньше проверялись только решения и только
  `changed`), корень по-прежнему несёт свой `support_check`.
- **`total_exact: false` при обрезке `max_nodes`**: узел, не попавший в
  бюджет, не раскрывается, его потомки не считаются — сочетание «неполное
  число / `exact: true`» запрещено.
- **`in_paths_capped` наследуется потомком**: ребёнок узла, упёршегося в
  потолок путей, тоже помечен (иначе усечённое число читалось как точное).

### Бюджет, который действительно ограничивает работу (F7–F12)

- **Хеш саммари решения идёт через `consume`** (F7): 10 МБ формулировки при
  бюджете в 1 байт дают `incomplete`, а не полный хеш и чистый вердикт.
  Замер в тесте через обёртку `node:crypto`: при бюджете 1 байт хешировано
  0 байт; при достаточном — саммари проходит через хешер и `claim_changed`
  выставляется.
- **Запасной путь снимков — точечное чтение по `edge_key`** (F8), без
  материализации всей активной истории пары. Замер на фикстуре «одна живая
  связь + 1000 активных снимков того же support с разными `edge_key`,
  минимальный бюджет»: материализовано строк **1000 → 2**.
- **Метрики под бюджетом** (F9): выборка решений идёт keyset-страницами,
  размер страницы ограничен остатком бюджета, `metrics_truncated`
  выставляется пробой `LIMIT 1` только когда решения реально остались
  непроверенными (семантика «исчерпание ровно на последнем — не обрезка»
  из 2.1.1 сохранена). Замер на 2000 решениях с бюджетом 1: материализовано
  строк решений **2000 → 1**.
- **`CheckBudget` валидирует аргументы** (F10): `NaN`/`Infinity`/отрицательные
  и дробные значения — ошибка конструктора, а не молча отключённый бюджет;
  0 остаётся допустимым (закрытый бюджет).
- **`consume` различает исчерпание и отказ** (F12): попытка сверх
  исчерпанного бюджета поднимает `exceeded`, точное исчерпание по лимиту —
  нет.
- **Мёртвые снимки идут keyset-страницами** (F11), а не `LIMIT/OFFSET`:
  страница стоит своих строк, а не повторного прохода префикса.

### Слияние: расхождение копий — конфликт, а не порядок (F2, изменение поведения)

Дедупликация рёбер при слиянии двух баз шла по ключу с `description`, а
уникальный индекс БД — только по `(from_id, to_id, relation)`. Живое ребро с
одним рационалом и надгробие того же ребра с другим считались разными: второй
`INSERT OR IGNORE` молча отбрасывался, и результат зависел от порядка входов —
при одном порядке оставалось живое ребро, при другом надгробие. Теперь
дедупликация идёт по тому же ключу, что и индекс, а расхождение `removed_at`
или `description` между копиями регистрируется как `needs_merge` (счётчик
`edgeConflicts` в отчёте слияния); правило «надгробие побеждает живое»
применяется внутри ключа. Слияние баз с расходящимися копиями одного ребра
теперь даёт помеченный конфликт вместо тихого выбора одной из сторон.

## 2.1.1

Четыре правки по ревью после 2.1.0 и ретеншн журнала вызовов. Новых
возможностей кроме ретеншна нет; схема поднимается на v10 (индекс живых опор).

### Честный контракт чтения (F1)

Описания `get_concept` и `provenance_trace` утверждали «чтение не пишет
ничего», при этом MCP-обёртка пишет строку телеметрии вызова в `timeline` на
КАЖДЫЙ вызов, включая чтение. Формулировка теперь точная: в граф и снимки эти
инструменты не пишут ничего; служебная телеметрия вызовов (`timeline`) ведётся
отдельно и на провенанс не влияет. Описание `provenance_audit` не менялось —
его журнал прогонов и правда единственное, что он пишет. Новый интеграционный
тест говорит с сервером по stdio (MCP) и закрепляет контракт на слое обёртки:
счётчики `nodes`, `edges`, `support_baselines`, `provenance_audit_runs` не
меняются, `timeline` растёт ровно на вызовы — телеметрию нельзя «убрать для
чистоты», не сломав тест.

### Индекс живых опор и keyset-пагинация (F2, схема v10)

Страничный запрос живых опор использовал `ORDER BY to_id LIMIT/OFFSET` —
каждая страница пересортировывала ВСЕ живые рёбра узла: звезда 20 000 опор с
бюджетом 1 платила за всю звезду. Теперь:

- схема v10: индекс `idx_edges_live_from_to` на
  `edges(from_id, relation, removed_at, to_id)`; миграция идемпотентная,
  старые базы получают индекс той же веткой при открытии (паритет со
  свежими);
- пагинация переведена на keyset: `to_id > последний ORDER BY to_id LIMIT n`
  — `to_id` уникален в паре (из `idx_edges_unique`), курсор не пропускает
  строки, работа страницы пропорциональна самой странице.

Бенчмарк `scripts/perf-trace.mjs` (медианы provenance_trace): звезда 10 000 —
232 → 213 мс, звезда 20 000 — 378 → 344 мс. `EXPLAIN QUERY PLAN` страничного
запроса — `SEARCH ... USING INDEX idx_edges_live_from_to`, без `SCAN` и без
`TEMP B-TREE`.

### Ретеншн журнала вызовов (F5)

`timeline` писала строку на каждый вызов инструмента, и чистки не было ни
какой — на активной базе десятки тысяч строк в том же файле, который агент
таскает с собой. Теперь:

- настройки `MEGAMEMORY_TIMELINE_RETENTION_DAYS` (по умолчанию 90) и
  `MEGAMEMORY_TIMELINE_MAX_ENTRIES` (по умолчанию 50000); `0` в любой из них
  — «не ограничивать», журнал ведётся целиком;
- очистка по возрасту и по количеству идёт при записи, не чаще раза в 500
  записей; удаление — пачками по 1000 строк, каждая отдельным statement'ом,
  без долгой блокировки (бэклог 100 000 строк чистится за секунды);
- `megamemory stats --prune` выполняет очистку вручную и печатает, сколько
  удалила;
- журнал аудита провенанса (`provenance_audit_runs`) не трогается: у него
  свой ретеншн (200 прогонов на узел / 90 дней, план-3 §10).

### Перенос происхождения через merge (F3, тесты)

Перенос `created_via` реализован во всех шести путях merge, но тест покрывал
только `agent` + `accepted_at`. Новый тест прогоняет все три значения —
`agent`, `auto` и ребро из базы без колонок провенанса (эмулируется схемой
до v8) — через ОБА порядка слияния: `agent` остаётся `agent`, `auto` —
`auto`, отсутствующее становится `unknown`.

### Честный `metrics_truncated` (F4)

Метрики провенанса считали `metrics_truncated = budget.exhausted`: бюджет,
кончившийся ровно на последнем решении, поднимал флаг — формально верно,
практически ложная тревога. Теперь флаг поднимается только когда после
исчерпания бюджета остались НЕобработанные решения. Мёртвая ветка
`view === null → unknown++` удалена: `WHERE` уже гарантирует каждому решению
якорь, живое ребро или строку снимка; на её месте non-null assert с
инвариантом — будущее изменение `WHERE` уронит тест громко, а не потеряет
решения из счётчиков тихо.

### Снимок обоснования: закрытие дыр подтверждения (план-4-fixes-6, схема v9)

Ревью Astra по заходу 5 (схема v8): P0 — нарушение инварианта «мутация не
подтверждает», P1 — тихая потеря сигнала, P2 — контракт и метрики.

- **F1 (P0)**: `create_concept` больше не подтверждает опоры из
  `input.edges` — снимок создаёт только `evidence`. Ребро из `edges`
  пишется, но пара остаётся `unknown` до явного `confirm_supports`: снимок
  по ребру закрепил бы саммари и статус цели, которых агент мог не читать.
- **F2 (P0)**: бюджет проверки ограничивает РАБОТУ, а не только вердикт.
  Опоры считаются до материализации (COUNT по индексу), читаются страницами

  обработано не больше бюджета.
- **F3 (P0)**: `confirm_supports` принимает `expected_status_digest` наравне
  с остальными digest'ами. Выбран отказ (не частичная запись): без поля или
  с несовпадением — `version_conflict`; агент не подтверждает статус,
  который не видел.
- **F4 (P0)**: сверка ожиданий и запись — одна транзакция `BEGIN IMMEDIATE`;
  независимый writer больше не может вклиниться между проверкой и записью.
- **F5 (P0)**: merge переносит снимок по ИДЕНТИЧНОСТИ ребра (исходный
  rowid → конкретная выходная строка, маппинг строится при переносе рёбер),
  а не по концам. Ребро, не пережившее merge, получает ключ с префиксом
  `dead:` — численно не совпадает ни с одним rowid, подтверждение не может
  «уехать» на новую связь с теми же концами. Из проверки убран fallback-якорь
  «последняя строка опоры»: новая пара после `confirm → unlink → link`
  остаётся непроверенной.
- **F6 (P0)**: решение, у которого сняли последнюю опору, попадает в
  `weak_links` как `support_changed`/`removed` — раньше ветка
  `supports.length === 0` молча пропускала непустой снимок.
- **F7 (P1)**: пустое подтверждение (`items: []`) НЕ стирает строки снимка —
  помечает их `superseded_at` (схема v8→v9, колонка аддитивна). «Подтверждена
  и снята» отличима от «опор никогда не было»: признак `had_supports` в
  `support_check` и счётчик `decisions_with_superseded_supports` в метриках.
  Повторное подтверждение той же пары снимает пометку.
- **F8 (P1)**: `decisions_by_check_state` считается по всем решениям со
  снимком или якорем формулировки, а не только с живыми рёбрами; решения без
  живых опор видны в отдельном счётчике `no_live_supports`.
- **F9 (P1)**: `created_via` и `accepted_at` переносятся при merge; источники
  без этих колонок честно дают `unknown`.
- **F10 (P2)**: перенос `claim_digest` узла через merge задокументирован как
  осознанный и проверен тестом: переносится СТАРЫЙ digest, а не текущая
  формулировка (расхождение `claim_changed` сохраняется).
- **F11 (P2)**: оборванная бюджетом проверка внутреннего узла видна:
  счётчик `inner_nodes_incomplete` в выдаче `provenance_trace` и деградация

- **F12 (P2)**: контракт «чтение не пишет» зафиксирован в описаниях

### Снимок обоснования: support_baselines (план 4 v8, схема v8)

- **`confirm_supports`** — отдельный вызов подтверждения опор: агент передаёт
  digest'ы прочитанных формулировок (`expected_claim_digest` решения +
  per-опорные `expected_claim_digest`/`expected_edge_digest`); любое
  расхождение с текущим состоянием — отказ `version_conflict`, ничего не
  записывается. Пустой `items` = подтверждение «опор нет» — валидное
  состояние, отличное от «не проверялось».
- **`support_check`** в `provenance_trace` (корень — всегда, внутренние узлы
  при `changed`) и на карточке `get_concept`: `unchanged` / `changed`
  (причины per опоры: `summary` | `status` | `rationale` | `removed`) /
  `unknown` / `incomplete` + `baseline_at` и `claim_changed`. `unknown` и
  `incomplete` чистотой не считаются — решение без снимка не показывается как
  проверенное.
- **Ни одна мутация не подтверждает**: link/update_concept/remove/merge/
  consolidate не пишут и не обновляют снимок. Единственное исключение —
  `create_concept` с `evidence` подтверждает версии, переданные в том же
  вызове (автовывод — нет). Чтения ничего не пишут.
- **Схема v8** (`user_version` 7→8, аддитивно): таблица `support_baselines`
  (строка на подтверждённую пару «решение — опора», БЕЗ каскадов — строка
  переживает удаление ребра и опоры, сигнал `removed` сохраняется),
  `nodes.claim_digest`/`claim_digest_at` (пишутся только подтверждением),
  `edges.created_via` (`agent`/`auto`/`unknown`, назначается серверным путём
  записи, от вызывающего не принимается; импорт и до-миграционные строки —
  честный `unknown`) и `edges.accepted_at` (явное принятие авто-ребра,
  `created_via` не переписывает).
- **Digest'ы**: `sha256("v1\n" + payload)`; payload саммари — только обрезание
  краёв и CRLF→LF, без внутренней нормализации («a  b» ≠ «a b»); у
  жизненного/эпистемического статуса опоры — свой `status_digest`, поэтому
  причины `summary` и `status` различимы по отдельности.
- **Бюджеты проверки**: `max_check_edges` (по умолчанию 5000) и
  `max_check_bytes` (по умолчанию 2 МБ) на вызов; при исчерпании —
  `incomplete`, вердикт `unchanged` не выдаётся. Списки id в выдаче
  ограничены (50 + честный итог).
- **weak_links**: новые записи `support_changed` и `support_unreviewed`;
  порядок приоритета — refuted → abandoned → cycle → support_changed →
  support_unreviewed → missing_support → no_support → ungrounded_support →
  no_rationale; маркер усечения несёт счётчики причин по всем порождённым
  записям.
- **Merge/импорт**: снимки переносятся вместе с решением, remap id и edge_key
  согласован, содержимое снимка не заменяется текущим; `confirmed_by`
  переписывается в `import`. renameNodeId (repair-ids, resolve_conflict)
  переносит ключи снимка; FK при переименовании переведены на
  `defer_foreign_keys` — rename узла с входящими рёбрами внутри внешней
  транзакции больше не падает.
- **Метрики** (CLI `megamemory stats`, секция Provenance): рёбра по
  происхождению (`created_via`), явно принятые (`accepted_at`), решения с
  живой опорой, решения по состоянию снимка — четыре разных числа, ни одно
  не подменяет другое.

  обход и новые записи; компонента закрыта для записей только входящих рёбер
  (`needs_merge`), после merge активных рёбер на надгробные узлы и петель не
  остаётся.

### Опоры: `evidence` и автовывод

- **Шорткат `evidence` в `create_concept`:** опоры объявляются в том же
  вызове — `{ref | node, why}`; файл без цитирующего узла получает узел-факт.
  Счётчик в ответе считает уникальные опоры.
- **Автовывод опор из `why` + `file_refs`** (`provenance.auto_ground`) — по
  умолчанию **выключен**: выведенные сервером опоры не выдаются за объявленные
  агентом.
- **Строгий режим `provenance.require_support`** (по умолчанию выключен):
  `decision` без единой опоры (evidence, ребро `informed_by` или автовывод)
  отклоняется с текстом «передай evidence в том же вызове». Флаг читается на
  каждом вызове без рестарта; переопределение окружением
  `MEGAMEMORY_PROVENANCE_REQUIRE_SUPPORT` / `MEGAMEMORY_REQUIRE_SUPPORT`.
  Другие типы узлов, `link` и чтение не затронуты.

### Сигнал «инструкции устарели»

- `install` ставит штамп `<!-- megamemory:instructions vX.Y.Z -->` в блок
  `AGENTS.md`/`CLAUDE.md` и в каждый сгенерированный `commands/*.md`; повторный
  `install` заменяет содержимое между маркерами и обновляет штамп.
- `list_roots` и `understand` возвращают `instructions_stale`,
  `instructions_version`, `server_version`: штамп сверяется с версией сервера
  на каждом вызове. Файла инструкций нет — `stale: false`, версия `null`.
  Агент stderr не видит — сигнал едет в ответе, который он и так читает.

### Гигиена удаления

- Удаление узла, на который опираются другие, отклоняется с подсказкой,
  называющей зависимые узлы; `force` переопределяет. Удаление — надгробие:
  история сохраняется, живые ответы его не видят.

### Поведение merge

- **Надгробие ребра побеждает живую копию** (вышло в 1.9.0-fork.1, включено в
  перечень, т.к. меняет поведение merge): снятая в одной базе связь не
  воскресает от того, что вторая ветка о ней не знает. Вернуть связь можно
  только явным `link`.

### Прочее

- Тест-гигиена: тесты установки больше не пишут в реальный профиль
  пользователя на Windows (`os.homedir()` игнорирует `$HOME`); все пути
  установки учитывают `$HOME`.

## Fork (1.9.0-fork.1)

### Слияние: надгробие ребра побеждает (план-3-fixes-2, F20)

- Если в одной базе ребро снято (надгробие), а в другой живо, merge больше
  не бросает монету: побеждает **надгробие** — снятая связь не воскресает
  от того, что вторая ветка о ней не знает. Вернуть связь можно только
  явным `link`. Ключ дедупликации рёбер теперь JSON-массив — пары id,
  содержащие `|`, больше не коллидируют (F11).
- **`provenance.auto_ground` по умолчанию `false`** (F19): опоры, выведенные
  сервером из `why` + `file_refs`, больше не выдаются за объявленные
  агентом — доля «решений с опорой» меряет работу агента, а не сервера.
  Включается явно в `megamemory.config.json` рядом с базой; выведенные
  опоры по-прежнему помечаются в ответе («Добавил опор по file_refs»).

### Провенанс: связь `informed_by` (план 4, схема v7)

- **Новая семантика `informed_by`** — «from материально опирается на to»
  (решение/вывод → доказательство, допущение, прошлый результат). Слой
  отдельный: `supersedes`/`contradicts` в проверке циклов не участвуют и
  обход `informed_by` не тянет их за собой; `parent_id` тоже.
- **Рационал обязателен и непуст:** в `description` — что именно в узле-to
  поддерживает from. Пустой — отказ («рационал обязателен: что именно в
  узле-to поддерживает from»). Формулировка продублирована в описаниях
  `link` и `create_concept` — это то, что реально видит агент.
- **Строгий DAG.** Отвергается `u → u` и `u → v`, если `v` уже достигает
  `u` по активным `informed_by`. Обход cycle-safe (visited set, без
  рекурсии по графу) — цикл, принесённый merge, не подвешивает новые записи.
- **Проверка и запись — одна транзакция** (`BEGIN IMMEDIATE`): два
  параллельных батча не могут оба пройти по одному снапшоту и вместе
  закоммитить цикл. `create_concept` с массивом рёбер валидируется по
  объединённому графу; нарушение откатывает весь батч — полузаписей нет.
- **Оживление надгробия через тот же чек:** если `u→v` снято, а потом
  добавлено `v→u`, оживление `u→v` отвергается. Re-link — оживление
  существующей строки, на тройку `(from, to, relation)` ровно одна строка.
- **Оба конца живы:** активное ребро на надгробный узел — ошибка, а не
  тихий обрыв (в `link`, в батче `create_concept`).
- **Merge:** файл с живой однострочной петлёй `u→u` отвергается целиком,
  до любых записей; после merge нет активных `u == v` и нет активных рёбер
  на надгробные узлы (такие строки отбрасываются); надгробия переносятся
  как история.
- **Карточка узла** (`get_concept`): блоки `informed_by` (на что опирается)
  и `informed_by_incoming` (кто опирается) с рационалами.
- **Схема v7:** только составные индексы `idx_edges_relation_from` /
  `idx_edges_relation_to` — колонок не добавлено. `PRAGMA user_version` = 7;
  `meta.schema_version` (маркер автоконвертации легаси) не тронут.
  Миграция идемпотентна.
- Чего в этом релизе сознательно нет (следующие этапы после замера
  полезности): `provenance_trace`, `provenance_audit`, отказ при удалении
  опорного узла, принуждение «decision без опоры отклоняется».

## Fork (1.8.0-fork.1)

### Workflow: reasoning trails, role slots, task board (plan 2, schema v6)

- **Цепочки рассуждений (trails):** упорядоченный список узлов + обязательная
  авторская сводка «почему решили так». Отпечаток смысла участника —
  `sha1(summary + epistemic_status + sorted(outgoing informed_by с рационалами))`;
  `name`, `parent_id`, timestamps сознательно исключены (переименование и
  merge не протухают цепочки). При чтении сравниваются с текущим состоянием:
  расхождение → `stale` (можно перечитать и пересобрать), участник удалён
  физически → `broken` (восстанавливать нечего). Откат текста к исходному
  честно возвращает «свежая».
- Инструменты: `trail_save` (сводка обязательна), `trail_get` (по-членно
  state + reason), `trail_refresh` (переснимок после проверки; на broken —
  отказ), `trail_extend`. В карточке узла — блок «участвует в цепочках»
  со state.
- **Новая связь `informed_by`** — провенанс вывода («вывод опирается на факт»),
  входит в отпечаток цепочки.
- Удаление участника цепочки никогда не молчаливо: `remove_concept` помечает
  цепочки устаревшими и перечисляет их в ответе с причиной (аудит B5).
- **Слоты ролей:** у роли ровно один живой держатель. Взятие новым узлом
  пишет ребро `supersedes` старому (старый не отзывается — вчерашняя передача
  смены остаётся правдивым документом); повтор тем же узлом — no-op;
  `release` освобождает роль, узел не трогает; скоуп — проект.
  Гарантия единственности — от сериализованного upsert в одной транзакции.
  Инструменты: `slot_set`, `slot_get`, `slot_release`, `slot_list`.
- **Доска задач:** колонки `task_state` (`open`/`done`) и `due_at` на узлах —
  отдельная ось, не пересекается с жизненным циклом (`status`) и
  эпистемикой (`epistemic_status`). Сортировка по «гниению»:
  `rot = возраст_дней + (изолирован ? 45 : 0) + (просрочена ? 400 : 0)`
  (константы kaeru, не менять без причины). `done` снимает `due_at`.
  Инструменты: `task_add`, `task_done`, `board`.
- Стартовая сводка (`list_roots` compact): слоты идут первыми, затем
  верхушка доски (5 карточек по rot).
- Схема: `PRAGMA user_version` 5 → 6 (таблицы `trails`, `trail_members`,
  `slots`; колонки `nodes.task_state`, `nodes.due_at` с частичными
  индексами). Свежие базы получают колонки сразу в `CREATE TABLE` — паритет
  с мигрированными. Идемпотентна.
- Версия пакета: 1.8.0-fork.1.

  edges with automatic status flip, `contradicts` surfaced in `list_concepts` conflicts;
  status badges, muted outdated nodes and "show outdated" toggle in the explorer.
- **T5 — consolidation**: embedding-similarity duplicate finder
  (`megamemory consolidate`), merge into the older node with edge transfer; explorer tab.
- **T6 — digest nodes**: per-module compression of ≥5 children into one `digest` node
  (summary ≤800 chars, file_refs ≤10), 0.8 search weight, auto-built after the 5th child,
  `megamemory digest`.
- **T7 — markdown export**: one file per node with frontmatter and wiki-links,
  deterministic order, `megamemory export --md <dir> [--check]` (exit 1 on drift, CI-ready).
- **T8 — token accounting**: every `understand`/`list_roots`/`get_concept` answer is
  measured; 7-day aggregates in `megamemory stats`, `/api/stats` and a Tokens panel
  in the explorer.
- **T9 — doctor**: `megamemory doctor` health-check (schema, model, FTS, ids, vectors,
  orphans, digests) with exit code 1 for CI.

Migration from upstream v1.6.2: run `megamemory migrate --dry-run`, then `--apply`;
data-changing id repair happens with a backup. See `docs/FORK.md`.

## 1.0.0 — Initial Release

### Features

- **MCP server** with 6 tools: `understand`, `create_concept`, `update_concept`, `link`, `remove_concept`, `list_roots`
- **Semantic search** via in-process embeddings (all-MiniLM-L6-v2, 384 dimensions) — no external API calls
- **SQLite persistence** with soft-delete, schema migrations, and WAL mode
- **Web explorer** — browser-based graph visualization with Cytoscape.js at `megamemory serve`
- **CLI** with colored output, graceful error handling, and interactive port conflict resolution
- **`megamemory init`** — one-command setup for opencode (MCP config, AGENTS.md, skill plugin, bootstrap command)
- **Concept kinds**: feature, module, pattern, config, decision, component
- **Relationship types**: connects_to, depends_on, implements, calls, configured_by
- **Knowledge graph** designed for LLM agents — concepts in natural language, not code symbols
