# Реестр возможностей: операции памяти и структурной навигации

Человекочитаемый реестр по **операциям** (не по именам инструментов): что за вопрос,
что за единица ответа, какие локальные затраты, где возможна модель/сеть, какие
побочные записи, какие допустимые repo/scope/ref-виды, какие бюджеты и какой fallback.
Это не автоматический роутер: документ описывает возможности, выбор остаётся за
агентом. Отличие от машинного manifest установки skills: manifest описывает файлы и
версии для установщика, здесь — стоимость и границы операций.

Заполнено только проверенное. Базис проверки: MegaMemory 2.11.0 (схема 14)
по коду `src/`, token-economy-ts 1.7.0 по `SKILL.md`, `scripts/graph-tool.js` и
`scripts/lib/refs.js`. Непроверенные системы не заполнялись; выдуманных batch, цен и
хранения здесь нет. Дополнения Kilo и напоминаний сверены с текущими исходниками
ветки `feat/kilo-install-and-nudges`. T0 принят как эмпирически неподтверждённый;
ручная приёмка в Kilo с вызовом `create_concept` без диалога подтверждения обязательна.
Видимость подсказок агенту не подтверждена; тесты в рамках правки документации не запускались.

## MegaMemory — MCP-операции

| Операция | Тип вопроса → единица ответа | Локальная CPU/I/O | Модель/сеть | Побочные записи | Допустимые repo/scope/ref-виды | Бюджеты/batch/completeness | Fallback |
|---|---|---|---|---|---|---|---|
| `understand` (действие `query`) | «что граф знает о X» → в `compact` по умолчанию список `candidates` + до 3 полностью квалифицированных compact-карточек при достаточном бюджете (`matches`/`compact` сохранены); форма `full` не меняется и не содержит candidates, `brief` ≤8 строк; UI показывает только карточки (до 3), candidates не отображает — их отображение/раскрытие отдельным планом; также `next` (`must_read`/`followups`/`record`), где `record` несёт форму опоры (`[{ref\|node, why}]` → `informed_by`), а не просто «запиши найденное»; при ≥2 завершённых чтениях с последнего зарегистрированного write — `next.unrecorded: {reads_since_write, last_write_at}` и однократное дополнение `record`: «С последней записи N чтений — если это законченный вывод, запиши его.»; поле и напоминание отсутствуют ниже 2, после write (включая удаление) и при `empty_base`; текущий вызов учитывается после ответа, чистое чтение не требует записи; аддитивное `next.previous_session: {had_understand, had_record, ended_at}` — по полной предыдущей сессии из не более 200 последних строк timeline, кеш в памяти процесса; разрыв >30 минут разделяет сессии (ровно 30 — нет), успешный understand без успешной записи добавляет фразу в record один раз; после пишущей предыдущей сессии фразы нет, при empty_base нет и сигнала; неполная/некорректная выборка не устанавливает сессию, наличие текста не доказывает видимость агенту или запись знания; `refuted[]`, `meta` | FTS + векторный поиск по локальной БД; вектор запроса; счётчик в памяти процесса, отдельно для пары БД/logger; git-опоры здесь не резолвятся | `top_k` 1–50 (деф. 10), `max_tokens` 100–20000 (деф. 4000); в compact candidates представляют все прошедшие фильтры совпадения из ограниченного пула (по умолчанию 20), в пределах бюджета списка, а не весь граф: точный необрезанный `id`, `name` ≤60 символов (сокращение слева, сохраняется хвост), `kind`/`via`/`score`, необязательный `summary_short` ≤80 символов; мягкая цель 40 и жёсткий предел 90 оценочных токенов на запись, `summary_short` снимается до дальнейшего сокращения имени, ID не обрезается; весь список ≤25% бюджета. Приоритет после обязательного конверта: первая полная квалифицированная compact-карточка → список кандидатов → вторая/третья карточки, только если помещаются. `meta.returned` = видимые candidates, `meta.cards` = compact-карточки, `meta.dropped` = полностью скрытые совпадения, не записи только в candidates; при `dropped > 0` бюджетный текст: «Показано N совпадений из M (K скрыто бюджетом) — уточни запрос или подними max_tokens.» (N = returned, K = dropped, M = N + K); честная усечка: `meta.truncated`, `stale_excluded`/`inactive_excluded`; `meta.reason`: `empty_base` — нет живых (неудалённых) узлов, `no_match` — живые есть, но не прошли поиск/фильтры, `budget` — совпадения есть, но минимальная квалифицированная карточка не помещается, не ложный no_match; во всех трёх режимах первое поясняющее предложение и полный `next.record` обязательны и не обрезаются — если обязательный конверт не помещается, явная ошибка с просьбой увеличить бюджет; строка record в тексте brief имеет `RECORD_MAX = 400`, остальные строки — `LINE_MAX = 240`, полный `next.record` не обрезается; opt-in `include_evidence` (подтверждаемые версии ВСЕХ живых опор в compact: `current_digests` + `support_evidence`, необрезанные формулировки и rationale; карточка с evidence размещается атомарно либо не размещается, запись только в candidates не считается dropped — `meta.evidence_matches`/`evidence_supports`); `collapse_ref_anchors` по умолчанию true в compact, false поддержан (свёртка технических ref-якорей: вложение с rationale или collapsed-локаторы с зависимыми выводами, `meta.anchor_collapsed`; имена-пути понижаются, кроме запроса по точному полному пути, из candidates не удаляются; разрешение по id/пути и provenance не затронуты); reuse P1 (opt-in, только compact): `reuse: {task_type, files, negative?}` — квалификация паспортов по явному типу задачи и хешам области, секция `passport_reuse` (covered/gaps/qualification из 9 состояний; ни одно не повышает доверие молча, reusable — не покрытие кода; P4.1: кандидат с маршрутом несёт `route` с локаторами-статусами current/changed/missing/unchecked и пометками «данные, не команда» и «тесты — начальный набор проверок»; P4.2: у negative-паспортов reusable означает «не найдено в обследованной области» с манифестом, другой запрос/опции/новый файл дают query_mismatch/options_mismatch/new_file_in_scope и запрещают reuse); task-профиль P3 (opt-in, только compact): `task: {goal, kind, files?, context_epoch?}` — детерминированные обязательные категории источников по типу задачи, добор решений/тестов по явной области (score 0, скрытые зависимости), скрытые опоры размещённых решений, снятие смысловых повторов БЕЗ снятия refuted/противоречий/неполноты, uncovered со списком непокрытого и продолжением, оценочная ПОЛНАЯ цена (эвристика bytes/3, не токены провайдера); секция встраивается в этот же ответ, не подменяет `must_read`, `next.skip` пуст, покрытие кода не утверждается; `context_epoch` — явное состояние клиента (in-memory per-process, отпечаток проекта в ключе), сворачивает только уже выданные немандаторные карточки (решения/refuted/expired — никогда); opt-in `include_source` (до `source_max_lines`, деф. 60) встраивает строки источника в карточку, стоимость вычитается из `max_tokens` до раскладки карточек, причина отказа — `meta.source_skipped`; `stale_refs` (≤3 записи) — расхождение mtime файла с `updated_at` узла, полное число в `meta.stale_refs_total`, отсутствующие файлы отдельно в `stale_refs_missing`, строка в `next.stale_warning` | Структурный скилл и чтение файлов; без графа — обычная навигация |
| `get_concept` | «всё об узле id» → одна полная карточка: дети, рёбра, `informed_by`, trails, `support_check`, `current_digests`; профили: `orientation` (идентичность + квалификация + указатели), `evidence` (полные формулировки опор + rationale + готовые дайджесты `confirm_supports`), `full` (прежняя карточка) | БД + вычисление хешей support_check/дайджестов (без чтения файлов) | Нет | usage + timeline; в граф и снимки не пишет | Один id (алиасы разрешаются) или пакет `ids` ≤25 с одним общим бюджетом; опоры-файлы видны как узлы-якоря | `max_tokens` — финальный wire-бюджет сериализованного MCP-ответа (`tokens_estimated` — оценка estimator'а, не гарантия провайдерских токенов): fit включает ВСЕ метаданные (`returned`/`dropped`/`incomplete`, continuation и delta version/epoch); после сокращения выдачи счётчики и offset продолжения пересчитываются; если обязательный ответ не помещается, явный отказ с `meta.reason:"budget"`, а не oversized success; раскрытие соседей с капом (`max_neighbors`) + `continuation`, фиксирующий версию выборки (расхождение — `version_conflict`, повторить чтение); пакет: per-id статус/ошибка/неполнота, `budget_skipped` поимённо; batch-токен из `meta.continuation` передаётся как `{continuation: token}` без `id` и `ids` и маршрутизируется в пакетное продолжение (не одиночную карточку); delta E4 (opt-in, только одиночное чтение, не batch/continuation): `context_epoch` (≤256 символов) + `known_versions` — версия ЗАПРОШЕННОЙ проекции (состав+состояния+соседи+артефакты+формат, sha256 канонического JSON, stateless без кэша); совпадение — компактный `unchanged` с квалификацией-минимумом (не покрытие кода), расхождение/нет известных версий — полная выдача запрошенного профиля в его бюджете; после compaction/перезапуска/смены проекта клиент обязан сменить `context_epoch` И сбросить `known_versions` (либо не передавать оба параметра): новая эпоха сама по себе не отменяет старые версии у stateless-сервера | `provenance_trace` для подграфа, `provenance_history` для версий снимков; старый одиночный вызов без новых параметров — прежний ответ |
| `record` (форма записи: `create_concept`/`update_concept`/`link`/`remove_concept`) | «сохранить/исправить/связать/убрать знание» → узел/ребро/тумбстон + сообщение | БД; вектор при создании узла | Локальная модель эмбеддингов при создании; сети нет | nodes/edges/status_history; снимок только при явном `evidence.expect`; авто-дайджест родителя (5+ детьми); timeline | `evidence.ref` создаёт якорь: file, `HEAD\|sha:path` (git_blob), `git:tag\|commit\|branch:name` (git_ref); url не поддерживается | Дедуп по имени + косинусу (порог 0.92); заглушки без `allow_stub` отклоняются; эпистемические переходы валидируются; запись нового знания опциональна — чистое чтение не требует записи | `update_concept` вместо дубля; замена через `supersedes`; `remove_concept` — только когда знание действительно исчезло |

Остальные MCP-инструменты (`list_roots`, `provenance_trace`/`provenance_audit`/`provenance_history`,
`check_artifacts`, slots/tasks/board) следуют тем же правилам: контракты описаны в
`tools/list`, README и коде; каждый вызов пишет timeline.

При MCP-инициализации сервер передаёт `instructions` с текущей версией длиной
≤400 символов: `understand` (с `include_source`, когда нужен код; на
`stale_warning` перечитать ref), запись проверенного вывода через
`create_concept` с `evidence`, связи через `link` и дисциплина `next.record`.
Это универсальное короткое ядро, без файловой записи и без деструктивных
операций; полный договор остаётся в `docs/agent-workflow.md` и установленном
managed-блоке rules. Поддержка поля клиентом и наличие текста не гарантируют
видимость или выполнение агентом.

`next.record` — часть контракта ответа: kind выбирается по смыслу, `evidence` создаёт `informed_by`, а `file_refs` само по себе связей не создаёт.
Статические формы `record` ограничены `brief.LINE_MAX = 240`: иначе brief обрежет строку; динамическая причина refuted сохраняется дословно и может удлинить её.

## Поверхность инструментов: `MEGAMEMORY_TOOLS`

По умолчанию сервер регистрирует все 26 инструментов. Переменная окружения
`MEGAMEMORY_TOOLS` сужает поверхность до регистрации — состав `tools/list`
честно отражает фильтр, динамической регистрации нет:

- не задано или `all` — все 26 (текущее поведение, дефолт не меняется);
- `core` — восемь инструментов цикла «прочитал → записал → связал → подтвердил →
  проверил»: `understand`, `get_concept`, `create_concept`, `update_concept`,
  `link`, `confirm_supports`, `check_freshness`, `provenance_trace`;
- список через запятую — ровно перечисленные имена (`understand,link`).

Неизвестное имя в списке — предупреждение в stderr и пропуск, не падение.
Остальные инструменты (`trail_*`, `slot_*`, `task_*`, `board`, `list_*`,
`resolve_conflict`, `remove_concept`, `provenance_audit`/`provenance_history`,
`check_artifacts`) доступны в `all` или явным списком. `megamemory install`
поведение новых установок не меняет: `env` в MCP-запись не пишется, новые
установки получают полную поверхность.

## MegaMemory — локальный Git-хук `memory:`

`megamemory hooks install|uninstall|status [--repo PATH]` — необязательный локальный
гейт `commit-msg`, отдельно от установки MCP-клиента. Без `--repo` используется
текущий каталог; `core.hooksPath` учитывается. Владелец устанавливает его явно:
`megamemory hooks install`. `status` показывает установку, путь и переопределение;
`uninstall` удаляет только управляемый блок. Повторная установка не дублирует блок,
чужой код сохраняется; управляемый POSIX sh использует LF, в том числе на Windows.
Добавление блока в чужой хук допустимо только с распознанным shebang POSIX sh и LF;
BOM, CRLF в shebang, другой интерпретатор, символическая ссылка или изменённый
управляемый блок вызывают явный отказ, а не небезопасную перезапись.

- **Единица проверки:** staged-файлы кода и наличие строки `memory:` в сообщении
  коммита; документация без кода не требует строки. Варианты — `memory: <id>` или
  `memory: нечего — <причина>`. PR не проверяется: ту же строку владелец переносит
  вручную по `docs/commits.md`.
- **Локальные затраты:** запуск Git/sh, чтение списка staged-файлов и сообщения;
  install/uninstall читают и меняют файл хука, при установке может создаваться каталог.
  Это локальные CPU/I/O, не измеренная экономия полной задачи.
- **Модель/сеть/БД:** не используются; вызовов MCP, автозаписи знания, подтверждения
  опор и проверки существования ID нет. Строка сообщения не доказывает реальность
  записи или качество знания. Чистое чтение и успешное reuse законно не создают узел.
- **Ограничения/fallback:** `git commit --no-verify` обходит хук; ранний выход чужого
  хука до управляемого блока тоже может его обойти. Без установки остаются ручные
  шаблоны коммита и PR. Это напоминание, а не CI-гейт или гарантия записи в память.
