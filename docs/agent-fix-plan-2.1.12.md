# План исправления MegaMemoryAgent после обзора 2.1.12

## Задача и исходные данные

Исправить подтверждённые дефекты бюджета контекста, файловых ссылок и безопасности веб-обозревателя; устранить пробелы в тестовом покрытии. Не менять архитектуру памяти и не смешивать исправления с масштабным рефакторингом.

База анализа: версия 2.1.12, ревизия `cefa02a`. Перед реализацией проверить актуальность участков ниже: номера строк — ориентиры, не устойчивые якоря.

Подтверждено исходниками:

- `src/tools.ts`, `listRoots`: при переполнении компактной выдачи возвращается полный список с описаниями, без обрезки.
- `src/artifacts.ts`, `checkArtifacts`: файловая ссылка передаётся в файловую систему целиком, включая суффикс строки.
- `src/web.ts`: `server.listen(port)` без ограничения интерфейса, нет авторизации, JSON/SSE доступны с `Access-Control-Allow-Origin: *`, есть изменяющий базу `POST /api/consolidate`.
- `vitest.config.ts`: стандартные проекты включают `src/__tests__`, но не `tests/integration`.
- `bench` измеряет получение контекста и нахождение ожидаемых узлов, а не качество и стоимость всей задачи агента. Это ограничение уже описано в `docs/bench-protocol.md`.

Не подтверждено независимо: результат 37 931 оценочных токенов, 64 теста выборочного CI, 661 успешный и 2 неуспешных теста nightly, причины двух падений, 20/25 попаданий демонстрационного поиска. Не использовать эти числа как собственные результаты без исходных логов и воспроизведения.

## Обязательные ограничения для исполнителя

1. Прочитать действующие инструкции проекта и загрузить `token-economy-ts`. Проверить доступность MCP `megamemory`; при доступности запросить знания по задаче до анализа кода.
2. Навигация и поиск — только инструментами скилла. Перед изменением общего файла выполнить `graph rdeps`. Файл от 300 строк: сначала `outline`, затем чтение нужных диапазонов.
3. Правки — точечные, по актуальному прочитанному тексту. Не перезаписывать большие файлы ради небольшой правки. Кодировка — UTF-8.
4. Не запускать тесты, сборку, линтер, dev-сервер, HTTP-сервер или экспериментальные прогоны без отдельного разрешения пользователя. Добавлять тесты можно; результаты проверок предоставляет пользователь или разрешённый CI.
5. Не коммитить, не пушить, не создавать PR и не выпускать релиз без явного поручения. План не разрешает эти действия.
6. Не менять паспорт проекта. В этой сессии `.zcode/rules/project-passport.md` не найден: перед реализацией уточнить актуальное расположение, если оно необходимо для соблюдения правил.
7. Существующие базы памяти не удалять, не переписывать и не использовать как тестовые фикстуры.

## Этап 1. Бюджет `list_roots`

**Приоритет: высокий.** Основные места: `src/tools.ts:1442–1516`, типы `ListRootsInput`/`ListRootsOutput` в `src/types.ts`, MCP-обработчик в `src/index.ts`, `src/__tests__/context-budget.test.ts`, `src/__tests__/usage.test.ts`.

### Изменения

1. Проверить контракт `max_tokens`, все потребители ответа и поля, которые MCP-обработчик добавляет после `listRoots`.
2. Удалить автоматический переход к расширенному ответу при переполнении. Переполнение должно уменьшать выдачу, а не увеличивать её. Не вводить новый полный режим без необходимости и согласования.
3. Считать бюджет по сериализованному ответу, включая `meta`, `hint`, `slots`, `board_top`, массивы и другие добавляемые инструментом поля. Проверить отдельно, не расходятся ли оценка функции и фактический MCP-ответ.
4. Сохранить приоритет стартового дайджеста: роли, затем задачи, затем корни. При переполнении сокращать менее приоритетные разделы; если не помещаются сами роли/задачи, ограничивать и их. У длинного элемента не должно быть возможности обойти бюджет.
5. Сохранять идентификаторы показанных узлов и `valid_until`. Использовать стабильный порядок. Не добавлять полные `summary` в компактную выдачу.
6. Отражать пропуски корней в `meta.returned`/`meta.dropped`. Если сокращены роли или задачи, сообщать это явно — не представлять частичную выдачу как полную.
7. Определить минимально допустимый бюджет по обязательному конверту ответа. Значения ниже него и некорректные числа отклонять понятной ошибкой; не обещать невозможное соблюдение лимита и не возвращать незаметно превышающий его ответ. Согласовать проверку на уровне MCP-схемы и прямого вызова функции.
8. Писать usage для всех успешных веток, включая обрезанную и пустую выдачу. Источник оценки и содержимое ответа должны совпадать. Избежать самопротиворечивого `tokens_estimated` после добавления метаданных.

### Тесты и критерии приёмки

- 100 корней с длинными описаниями при `max_tokens: 1500`: ответ остаётся компактным, показывает пропуски и укладывается в собственную объявленную оценку бюджета.
- Длинные имена, идентификаторы, роли, названия задач; русский текст, CJK и emoji не обходят лимит.
- Пустая база, небольшая база, большой бюджет, минимальный допустимый бюджет и ошибочные значения.
- В обрезанных ответах корректны usage, счётчики пропусков и `valid_until`.
- Проверка бюджета относится к реально возвращаемому объекту, а не к промежуточной проекции без служебных полей.

## Этап 2. Файловые ссылки с номерами строк

**Приоритет: высокий.** Основные места: `src/artifacts.ts:65–105,234–339`, `src/bench.ts:249–263`, `src/tools.ts` — создание опор, `src/guide.ts:59–68`, тесты artifacts/bench и документация форматов ссылок.

### Изменения

1. Найти все существующие механизмы разбора и нормализации ссылок. В `bench` уже есть `splitRefSuffix` для `path:line` и `path:line-line`; не создавать второй несовместимый контракт.
2. Выделить общий разбор в подходящий существующий низкоуровневый модуль либо создать его разрешённым инструментом скилла. Не импортировать весь `bench` в `artifacts` ради одной функции.
3. Поддержать файловые формы `path`, `path:12`, `path:12-30`, `path#L12`, `path#L12-L30`. Дополнительные варианты добавлять только при наличии существующего контракта или отдельного требования.
4. Для доступа к файловой системе использовать чистый путь. Для отображения и сохранения связи с доказательством сохранять исходную ссылку и локатор строк.
5. Не менять существующие идентификаторы опор и ключи `node_artifacts` без отдельного обоснования: новая нормализация пути не должна потерять baselines или создать дубликаты опор.
6. Проверять схемы git до файловой нормализации. Не отрезать части `git:tag:...`, `git:commit:...`, `git:branch:...` и существующих ссылок на git blob. Отдельно проверить политику локаторов у git blob; не расширять её случайно.
7. Сохранить Windows drive letters, UNC-пути и двоеточия внутри имени. Отделять только распознанный конечный локатор; не удалять произвольное содержимое после `:` или `#`.
8. Для неоднозначных имён настоящих файлов, похожих на локатор, определить документированное поведение. Не объявлять произвольное удаление суффикса безопасной универсальной нормализацией.
9. Хэшировать весь файл, как сейчас. Проверка диапазона строк и истинности решения не входит в эту правку; документация должна прямо отделять локатор от области хэширования.

### Тесты и критерии приёмки

- Ссылки на временный существующий файл с каждым поддержанным локатором успешно проверяются; при одинаковом содержимом получают одинаковый SHA-256.
- Изменение файла обнаруживается и через ссылку с локатором; исчезновение файла корректно отмечается как `missing`.
- Русские пути, Windows-пути, UNC, двоеточия и `#` в именах, некорректные суффиксы и git-схемы не ломаются.
- Первая проверка уже сохранённой ссылки после обновления не создаёт ложного изменения идентичности опоры.
- `bench` и `check_artifacts` одинаково понимают поддержанные файловые формы.

## Этап 3. Безопасный локальный веб-обозреватель

**Приоритет: высокий.** Основные места: `src/web.ts:53–58,96–134,594–638,788–813,844–871`, CLI в `src/index.ts`, интерфейс в `web`, интеграционные тесты сервера.

### Границы решения

В рамках исправления обозреватель остаётся локальным инструментом, не общим командным сервисом. Не добавлять публичный bind, аккаунты, произвольный CORS allowlist или удалённый доступ. Если такой режим нужен, запросить отдельное решение пользователя о модели доступа.

### Изменения

1. Явно привязать сервер к loopback, например `127.0.0.1`; печатать фактически доступный адрес. Если требуется поддержка IPv6, реализовать её явно, не возвращаясь к wildcard-bind.
2. Удалить `Access-Control-Allow-Origin: *` из JSON и SSE. Для штатного интерфейса на том же origin междоменный доступ не нужен.
3. Проверять `Host` по разрешённым локальным адресам и фактическому порту, не доверять `X-Forwarded-Host`. Это отдельная защита от DNS rebinding; одного loopback-bind недостаточно.
4. Для запросов с `Origin` отклонять чужой origin. Для изменяющей операции требовать штатный same-origin запрос браузера; не полагаться только на отсутствие CORS-заголовка. Если обнаружится законный небраузерный потребитель POST без `Origin`, согласовать безопасный способ доступа, а не оставлять исключение автоматически.
5. Для `POST /api/consolidate` требовать `Content-Type: application/json`, ограничить размер тела до разумного небольшого лимита, валидировать поля и обрабатывать ошибки чтения. После ошибки не изменять базу и не отправлять ответ повторно.
6. При необходимости добавить CSRF-механизм для штатного интерфейса, но не выдавать его за авторизацию удалённого сервиса. Сначала проверить, достаточно ли выбранного строгого same-origin контракта для фактических потребителей.
7. Не ломать GET графа, поиска, экспорта, истории и SSE; не изменять безопасность MCP через stdio под видом исправления обозревателя.
8. Обновить справку: локальный интерфейс, отсутствие поддержки командного сервиса, последствия изменения прежнего сетевого доступа.

### Тесты и критерии приёмки

- Сервер слушает только выбранный loopback; адрес в выводе соответствует bind.
- Штатный интерфейс, GET/SSE и допустимое слияние работают на том же origin.
- Чужие `Host` и `Origin`, некорректный Content-Type, невалидный JSON, неверные поля и превышение лимита тела отклоняются. База после запрещённого POST неизменна.
- В ответах нет wildcard CORS; чужому origin не выдаётся разрешающий CORS-заголовок.
- Проверку браузера/сервера выполнять только после разрешения пользователя и загрузки подходящего browser-use скилла.

**Приоритет: средний.** Основные места: `vitest.config.ts`, `.github/workflows/ci.yml`, `.github/workflows/nightly.yml`, `.github/workflows/publish.yml`, `tests/integration/serve.test.ts`, тесты конфигурации и найденные падающие тесты.

2. Если тест зависит от личной/неотслеживаемой базы, создавать минимальную SQLite-фикстуру в отдельном временном каталоге с текущей схемой и очищать её после закрытия всех соединений. Не подменять отсутствие данных пустыми ожиданиями и не скрывать падение через skip.
3. Проверить случайное наследование `MEGAMEMORY_DB_PATH` и других настроек из окружения. Тесты должны получать явные пути и восстанавливать изменённые переменные.
4. Разделить быстрые unit/db проверки и реальные CLI/HTTP-интеграции. Добавить `tests/integration` в отдельный явно названный Vitest-проект и полный прогон; обновить тесты самой конфигурации.
5. Учесть, что текущая HTTP-интеграция запускает `dist/index.js`. Полный разрешённый CI должен собрать актуальный `dist` до запуска; не проверять случайно оставшуюся старую сборку.
6. Проверить готовность сервера и гарантированное завершение дочернего процесса до удаления базы. Существующий выбор случайного порта не считать гарантией отсутствия конфликта; обеспечить предсказуемый старт без интерактивного запроса порта.
7. Не смешивать проверку HTTP-маршрутов с обязательным скачиванием модели: где семантическая модель не является предметом теста, использовать предусмотренный проектом FTS-режим. Модельные проверки оставить отдельными и явно обозначенными.
8. Сохранить быстрый CI, добавив в него регрессии этапов 1–3. Отдельно обозначить полный прогон с интеграциями и порядок его запуска. Изменение обязательности полного CI перед merge/release согласовать с пользователем.
9. Не утверждать, что полный набор зелёный, по успешному выборочному прогону. В отчёте приводить команду, ревизию, состав проектов и реальные результаты.

## Этап 5. Документация и измерение эффективности

**Приоритет: средний; не блокирует исправление дефектов.** Основные места: `README.md`, `README.ru.md`, `docs/bench-protocol.md`, `src/guide.ts`, описание метрик bench/usage.

1. Сохранить уже существующее различие между `bench` и A/B-протоколом живого агента. Не создавать ещё один конкурирующий документ и не представлять существующее описание как отсутствовавшее.
2. Проверить рекламные формулировки и подписи счётчиков: оценочные токены выдачи, стоимость получения контекста, hit rate поиска — не доказанная экономия всего выполнения.
3. Для будущего A/B-измерения учитывать наполнение и обновление памяти, MCP-вызовы, повторное чтение источников, подтверждение оснований, ошибки и исправления. Отдельно показывать холодный старт и повторное использование памяти.
4. Измерять стоимость всей задачи по реальным данным провайдера и время выполнения; качество оценивать по заранее подготовленным ожидаемым результатам. Проверять задачи «где», «почему» и задачи после изменения источников. Фиксировать число повторов и условия сравнения.
5. Сокращение стоимости считать выигрышем только при сопоставимом качестве. Не превращать hit rate ожидаемого узла в оценку правильности итогового ответа.
6. Не добавлять в проект чужие непроверенные числа как собственный benchmark. Реальные измерения выполнять отдельным согласованным экспериментом; не отправлять код, память или логи внешнему сервису без разрешения.
7. В описании работы уточнить: проект читает подключённый ИИ-агент; сервер предоставляет память и инструменты. Не обещать автономное AST-понимание или доказательство истинности через хэш.

## Этап 6. Итоговая приёмка и передача результата

Исполнитель должен представить:

- Список изменённых файлов и краткое объяснение каждого исправления.

Готовность: подтверждённые дефекты исправлены; регрессии покрыты тестами; разрешённые проверки прошли либо явно отмечены как ожидающие выполнения пользователем. Не объявлять задачу полностью проверенной до получения результатов.

Изменение версии, CHANGELOG, git-коммит, push, PR и релиз — отдельное поручение пользователя. Миграция базы для этих исправлений по умолчанию не нужна; если реализация требует её, остановиться и согласовать причины и совместимость.
