# Локальная телеметрия (J0)

Локальный сбор событий вызовов MCP-инструментов для последующего измерения
полной стоимости задачи (план 20+21 v3 §15.J0). Данные никуда не
отправляются: это append-only JSONL-файл на той же машине. Схема базы
данных телеметрией не меняется — никаких новых таблиц и колонок.

## Включение и отключение

Телеметрия **выключена по умолчанию**. Включение — явная переменная
окружения:

```
MEGAMEMORY_TELEMETRY_PATH=C:\path\to\telemetry.jsonl
```

- Значение — путь к JSONL-файлу; каталог создаётся при первой записи.
- Отключение: снять переменную (или задать пустую) и перезапустить сервер.
- Файл принадлежит владельцу: сервер его не ротирует и не удаляет. Файл
  растёт; очистка/архивирование — решение владельца (достаточно удалить
  файл при выключенном сервере).

При выключенной телеметрии накладных расходов на вызов нет: обёртка
регистрации не устанавливается, ответы не сериализуются и не разбираются
вторично. При включённой запись синхронная и дешёвая; сбой записи журнала
никогда не ломает вызов инструмента.

## Что собирается

Одна строка JSON на один вызов MCP-инструмента:

| Поле | Значение |
|---|---|
| `v` | версия формата события (сейчас 1) |
| `ts` | время события (UTC, ISO-8601) |
| `tool` | имя инструмента |
| `outcome` | `ok` / `no-op` (дубль create, пустой update) / `error` |
| `write_category` | категория записи, если известна структурно: `knowledge` / `confirmation` / `maintenance` / `no-op`; иначе `null` |
| `write_category_unavailable` | `true`, когда категория неизвестна структурно |
| `response_bytes` | объём сериализованного wire-ответа; `unavailable` у ошибок без ответа |
| `latency_ms` | время вызова обработчика |
| `must_read_refs` | ref-строки must_read из ответа `understand`; `unavailable`, если рекомендаций не было |
| `issued_nodes` | выданные узлы (id/статус) из ответа; `unavailable`, если неприменимо |
| `facts` | факты вызова: `cards_opened` (get_concept), `confirmations` (confirm_supports), `writes` |
| `provider_usage` | всегда `"unavailable"` сейчас: сервер не видит usage провайдера; клиентский журнал — отдельная задача (J1) |
| `error` | сообщение ошибки (зачищенное), только для `error` |

Честность:

- отсутствующие поля помечены `unavailable` — они не превращаются в нули;
- открытие карточки (`cards_opened`) — факт вызова `get_concept`, а не
  доказательство понимания текста агентом;
- `must_read_refs` — выданные рекомендации; чтение файлов агентом сервер
  не наблюдает. Легаси-счётчик воронки `must_read_opened` (в `stats
  --funnel`) по-прежнему считает вызовы `get_concept` после выдачи — это
  явно описано в его выводе и не переинтерпретируется.

## Приватность

- Payload'ы целиком не пишутся: запросы, тексты карточек и содержимое
  ответов в журнал не попадают — только метаданные вызова.
- Значения ключей и токенов зачищаются известными паттернами
  (`api_key=…`, `token: …`, `Authorization: …`, `Bearer …`,
  распространённые форматы токенов) в единственных строках, которые могут
  их эхоить — сообщениях об ошибках. Фильтр не претендует на полноту, поэтому
  полные payload'ы не пишутся вовсе.
- Журнал остаётся на машине и никуда не отправляется; делясь им
  (например, в отчёте), владелец отвечает за его содержимое.

## Ограничения

- Телеметрия видит только вызовы MCP-инструментов сервера: CLI-команды
  (`stats`, `doctor`, …) и чтение файлов агентом не наблюдаются.
- Объём и latency — метаданные одного вызова; полная стоимость задачи
  (инструкции, чтение исходников, provider usage, повторы) собирается
  отдельно (J1) и из этого журнала не выводится.
